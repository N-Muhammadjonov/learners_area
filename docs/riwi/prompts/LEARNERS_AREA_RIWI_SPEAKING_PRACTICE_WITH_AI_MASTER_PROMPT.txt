0. PURPOSE OF THIS FILE
======================================================================

This file is a complete implementation handoff for Arena / GPT Work / a senior
full-stack engineer.

The task is NOT to create a new Speaking module.

The task is to extend the EXISTING Learners Area Speaking architecture, especially:

    Speaking
      └── Practice with AI

so that the student can:

1. enter Practice with AI;
2. test the microphone before a session;
3. start an examiner-style session;
4. receive randomized questions from the existing canonical Speaking question bank;
5. stay on the SAME topic for an examiner-like cluster of questions before moving on;
6. press Start Answer;
7. speak into the microphone;
8. have the audio recorded while the spoken words appear live as text;
9. press Stop;
10. NOT have the answer auto-submitted;
11. review the transcript;
12. edit the transcript if Speech Recognition made a mistake;
13. delete/re-record the answer if desired;
14. press "Send to RIWI" only when satisfied;
15. see "RIWI is evaluating your answer...";
16. receive evidence-based feedback;
17. choose "Try again" or "Next question";
18. complete the selected Part/session;
19. receive appropriate part/session feedback and score only where justified;
20. preserve the recording, transcript provenance, evaluation provenance and history.

This feature must support two evaluation modes:

A. EXTERNAL-ASSISTED RIWI
   External AI performs the semantic/evaluation reasoning.
   Learner-facing attribution remains "Checked by RIWI".
   Internal provenance records the real provider/model/fallback truth.
   RIWI remains controller, validator, security layer, memory layer and learning layer.

B. LOCAL RIWI FALLBACK
   If no external AI is configured/available, RIWI uses its existing local
   deterministic evaluator and canonical Learners Area data.
   It MUST NOT fake capabilities that the local evaluator does not possess.
   It may assess transcript-derived signals honestly.
   Pronunciation remains NOT ASSESSED unless a genuine acoustic provider exists.

The initial Speech-to-Text path must use browser SpeechRecognition /
webkitSpeechRecognition when available, so the website owner has no separate
per-minute STT API cost for that path.

Audio recording continues to use the existing browser MediaRecorder /
Learners Area recorder architecture.

5. THE MOST IMPORTANT UX RULE
======================================================================

STOP DOES NOT MEAN SUBMIT.

The lifecycle is:

    RECORD
      ↓
    STOP
      ↓
    REVIEW
      ↓
    EXPLICIT SEND TO RIWI
      ↓
    EVALUATE

NOT:

    RECORD
      ↓
    STOP
      ↓
    AUTO SUBMIT

The student owns the review step.

After Stop, the student may:

    [ Edit transcript ]
    [ Delete / clear transcript ]
    [ Record again ]
    [ Play audio ]
    [ Send to RIWI ]

No evaluation starts until:

    Send to RIWI

is explicitly pressed.

8. MICROPHONE CHECK — REQUIRED BEHAVIOR
======================================================================

The microphone check occurs before the student starts the session.

It must:

1. request microphone permission;
2. confirm browser recording support;
3. verify that non-zero audio energy is arriving;
4. show a simple visual meter;
5. release the microphone after the check;
6. never keep the microphone open unnecessarily;
7. offer retry;
8. provide truthful unsupported/denied/error state.

Suggested state:

    idle
    requesting_permission
    checking
    passed
    denied
    unsupported
    error

Optional:
    2–3 second sample playback.

Do not upload the microphone-check sample.

Do not create a Speaking attempt for microphone check.

======================================================================
9. SESSION RANDOMIZATION — EXACT PRODUCT RULE
======================================================================

Every NEW Practice with AI session should feel different.

Do not simply take the first rows of each topic every time.

However:

RANDOM DOES NOT MEAN CHAOTIC.

The examiner must remain on one topic long enough.

Required topic-cluster rule:

    MIN questions per chosen topic = 3
    DEFAULT questions per chosen topic = 4
    MAX questions per chosen topic = 6

If a canonical topic contains fewer than 3 published eligible questions:

    do not invent questions;
    use the real available count;
    record the limitation.

If a topic has 10 questions:

    choose a random non-repeating subset of 3–6 according to session plan.

The AI MUST NOT do:

    Topic A question 1
    Topic B question 1
    Topic C question 1
    Topic A question 2

Instead:

    Topic A Q1
    Topic A Q2
    Topic A Q3
    Topic A Q4
       ↓
    Topic B Q1
    Topic B Q2
    Topic B Q3
       ↓
    next section

10. EXAMINER-LIKE PART FLOW
======================================================================

FULL SESSION:

    Part 1
      ↓
    choose random published Part 1 topic A
      ↓
    ask 3–4 questions from topic A
      ↓
    optionally choose Part 1 topic B
      ↓
    ask 3–4 questions from topic B
      ↓
    Part 2
      ↓
    choose one random published cue card
      ↓
    60 sec preparation
      ↓
    up to 120 sec answer
      ↓
    Part 3
      ↓
    prefer a topic semantically/canonically connected to the Part 2 topic
      ↓
    ask 3–6 questions
      ↓
    final session summary

PART 1 ONLY:

    one or more Part 1 topic clusters
    per-answer feedback
    no fake full IELTS overall band

PART 2 ONLY:

    one cue card
    feedback
    part/session estimate may be shown with honest limitation

PART 3 ONLY:

    one discussion topic
    3–6 questions
    per-answer feedback
    part/session summary at the end

Do not invent questions outside the canonical speaking_prompts bank unless a
future owner requirement explicitly enables generated questions.

11. SESSION PLAN MUST BE STABLE AFTER START
======================================================================

Randomization happens when the session is CREATED.

After creation, the selected plan must remain stable.

Refresh must NOT silently reshuffle the active session.

Store:

    selected prompt IDs
    topic order
    part order
    current position
    startedAt
    completedAt
    session mode

A new session may randomize again.

The same active session must not.

======================================================================
13. TRANSCRIPT DATA MODEL — REQUIRED PROVENANCE
======================================================================

Current transcript origins:

    stt
    manual

Browser Speech Recognition introduces a third truthful state.

Recommended origin:

    browser_stt

Current schema may need a length/validation update.

Do NOT silently label browser STT as server STT.

Do NOT silently label it manual.

Recommended fields:

    transcript
        final transcript sent for evaluation

    transcript_origin
        browser_stt | stt | manual

    transcript_provider
        null for browser SpeechRecognition
        provider id for server STT

    transcript_raw
        original browser transcript before student edits
        OPTIONAL but strongly recommended

    transcript_edited
        boolean

    transcript_edited_at
        nullable timestamp

Important security/product truth:

Browser Speech Recognition output is user-side data.
Even if the UI generated it, the server must not treat it as privileged truth.

The student may edit it.

The UI should state:

    Transcript generated from your microphone.
    Review it before sending.

If edited:

    Edited by you

must be recorded.

======================================================================
14. WHY RAW + EDITED TRANSCRIPT MATTERS
======================================================================

Example:

Spoken audio:
    "I worked there for three years."

Browser STT:
    "I work there for three years."

Student corrects transcript:
    "I worked there for three years."

The final evaluation is based on the corrected transcript.

Therefore RIWI MUST NOT later claim:

    "You pronounced / worked / incorrectly"

or:

    "The audio proves..."

The evaluator received an edited textual representation.

Keep the audio for replay/history and future acoustic analysis,
but the current transcript evaluator assesses the submitted text.

22. EXTERNAL AI UNAVAILABLE — LOCAL RIWI FALLBACK
======================================================================

Use the existing local RIWI Speaking evaluator.

Current local capabilities include transcript-derived signals such as:

- answer length;
- word count;
- approximate speaking rate when duration exists;
- filler/hesitation tokens when transcribed;
- discourse markers;
- repeated content words;
- vocabulary diversity signals;
- grammatical pattern issues;

- real intonation;
- word stress;
- phoneme accuracy;
- audio pause timing unless actually measured.

32. QUESTION RANDOMIZATION ALGORITHM — EXAMPLE
======================================================================

Pseudo-code:

function buildSessionPlan(prompts, mode, rng):
    published = onlyAuthorizedPublished(prompts)

    if mode includes Part 1:
        groups = groupByTopic(published, "part1")
        shuffle(groups, rng)

        select 1 or 2 topic groups depending session mode
        for each selected topic:
            n = boundedQuestionCount(group.size, min=3, preferred=4, max=6)
            choose n unique random prompts
            append contiguously

    if mode includes Part 2:
        group = random Part 2 topic
        cue = random cue from group
        append cue
        remember cue topic key

    if mode includes Part 3:
        prefer group matching/related to Part 2 topic
        else random Part 3 group
        n = boundedQuestionCount(group.size, min=3, preferred=4, max=6)
        choose n unique prompts
        append contiguously

    persist immutable plan

Important:
    no duplicates inside a session
    no unpublished prompt
    no unauthorized prompt
    no random question generation
    stable after persistence
