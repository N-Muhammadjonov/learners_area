# V5 adapter contracts — complete Phase 1 clients, backend unchanged

Extends V4/V3/V2 exact contracts, not a backend implementation. **`/api/frontend/public`, `/api/frontend/session`, `/api/frontend/view` are proposed and do not exist in production because of this migration.** Standalone preview `/api/*` returns503. Fixture handlers exist only in Playwright, not the preview/runtime. Do not mistake a missing live adapter for the remaining ordinary frontend engines/actions outside Phase1.

All proposed projections require authenticated server ownership where applicable, no-store private responses, normal origin/CSRF/session safeguards and redaction. Session invalidation rereads authoritative projection; BC/storage hints only invalidate and cannot supply role/status/identity. Unknown/expired/unauthorized projections fail closed. `401` revocation, `403` eligibility/permissions, `400/422` validation, `409` conflict, `429` throttling and `5xx` unavailable remain server categories; no driver strings are rendered. Timeouts/network/parse/malformed-ACK are localized native error states. No live behavior has been verified.

## Existing Phase 1 account/provider APIs

V4's exact login/recovery/register/reset/onboarding/admission/logout/auth-state/Telegram/search contracts remain in force. Important precise constraints and current consumers:

- `POST /api/auth/login` / `/api/auth/recovery/login`: `{email,password}`; successful login requires `ok:true` (or original `success:true` variant), boolean `onboarded` and valid `accountStatus`. Server issues HttpOnly session, policy/rate/eligibility; native never creates role. `modules/auth/password-form.js`, `js/adapters/account.js`.
- Register `{name,email,password,gender:'male'|'female'}`; reset request `{email}`; reset confirm `{token,password}`. Strict `ok:true`. Original server validates uniqueness/strength/token expiry/single use and revocation. Generic reset done does not prove delivery. Development reset URL restricted to same-origin `/reset-password/confirm` with token; never stored/logged.
- `POST /api/onboarding`: eight existing source fields `preferredLanguage`, `currentLevel`, `currentBand`, `targetBand`, `examDate`, `dailyStudyMinutes`, `strongestSkill`, `weakestSkill`; preferred EN/UZ; level A2/B1/B2/C1/C2; skills listening/reading/writing/speaking; numeric band/current optional0–9, target4–9 step0.5; daily5–600; date optional native ISO date. Existing endpoint applies authoritative validation, own profile update and onboarding eligibility; ACK then session reread. Native localized form does not grant admission.
- `POST /api/admission/request`: `{message?:string}` (trim/max1000 in native); own pending/rejected account, no client approval/role/userId. Existing handler's malformed-message fallback stores null rather than granting arbitrary input; integration must preserve/review original semantics rather than silently inventing an API. Strict `ok:true` acknowledges request, not approval. Duplicate open requests server-owned.
- `POST /api/auth/logout`: own current session only, existing body/cookie clearing; `ok:true` before success UI. `GET /api/auth/state` and existing session-access event/reconciliation transport remain original authority. SSE/reconnect/expiry/hints owned by private scope, no credentials in localStorage.
- Telegram intent create/status/exchange/cancel and legacy SDK/Google redirect remain original endpoints; V4 specifies exact nonce, purpose, status and response fields. Native `modules/auth/telegram.js` handles five-minute lifecycle, confirmed-only exchange, cancellation and link purpose. No endpoint accepts browser-assigned identity/role/admission. External widget remains blocked by standalone self-only script CSP; do not weaken CSP to manufacture integration success. Google/Telegram/server cookies/nonce exchange require an approved integration environment, not secrets in chat.

## Existing shell/shared API clients

Original search `GET /api/search?q=...` is V4-complete: minimum2 chars/debounce280ms, safe-local links, loading/error/empty/keyboard/focus/cancel. Server independently filters permissions/enrolment/publication/ownership. Native prefetch is bounded JS code only, never result/private data/media.

Notifications: existing `GET /api/notifications?count=1` → `{ok:true,unread:nonnegativeSafeInteger,notifications:[]}`; bell is an inbox link with source count badge, NOT a dropdown. Full `GET /api/notifications` → `{ok:true,unread,notifications:ownedRows}`; rows have safe id/title/body/createdAt/readAt/href, validated before render. Existing **`POST /api/notifications`** consumes exactly `{ids:[UUID,...]}` (max100) or `{all:true}` → `{ok:true,unread:nonnegativeSafeInteger}`; native rejects false acknowledgement/invalid counts before publishing. There is no invented `/api/notifications/read` endpoint. Source `src/app/api/notifications/route.ts`, `src/components/shell/{NotificationBell,NotificationRead}.tsx`; server owns authenticated-user filtering/update ownership/private no-store. Native `modules/shell/notifications.js`, `modules/shared/notification-read.js`, `js/adapters/notifications.js`: visible-only count refresh, opaque deduplicated invalidation, half-visible row observation,300ms batched serialized acknowledgements, read-all failure/retry and bounded attachment/abort cleanup. Full notification inbox frontend now closes with original-page audit and12 width/locale/theme journeys covering load/malformed/retry/read-all/reload/deep-query/hash/empty; no live delivery or staff notification creation is inferred.

`POST /api/support/reports`: `{route:internalPath(1..200),module:string(1..60),message:string(3..2000),viewport?:string(max20),lastErrorCode?:string(max120),build?:string(max60)}`. Native sends route pathname without query, actual module, trimmed message (min3), viewport and sanitized optional last error; it does not send build/identity/credentials. Existing source server validates limits and own active authenticated actor. Native `modules/shared/report.js` retains panel draft/error/retry and requires `ok:true` (server also returns `id`, not required by this consumer) before sent state. Original `src/app/api/support/reports/route.ts` and `src/components/support/ReportProblem.tsx`; no arbitrary SQL/errors/role fields. Panel is inline/floating, NOT an invented modal. Grammar/profile module tags deliberately correct the original `app` first-segment fallback. Staff report resolution remains Phase8 work, not closed by this consumer.

`POST /api/theme`, `/api/locale`: existing narrow `{theme:'day'|'night'}` / `{locale:'en'|'uz'}` presentation cookies; require `{ok:true}`. No identity/permissions in preferences. Error does not silently commit a preference. `js/preferences.js`, `js/components/controls.js` own pending/serializing, locale mutation wait, same-route draft/focus/scroll and cleanup.

Shared ConfirmAction/ConfirmSelect/AsyncAction completion means their native lifecycle contract works with an ACK/rejected/aborted caller; it does NOT close every staff mutation caller or claim server authorization. Those source action adapters still require their own Phase8 audits.

## Integration boundary

Public/session/profile/pending projections, real auth/provider/session-cookie/CSP/media integrations and all live acceptance require owner-approved existing server services in nonproduction. No new production APIs/backend/Python/DB/provider/Telegram/Railway/Cloudflare/R2/DNS configuration, records or secrets were changed. All educational/grading/media/staff adapters remain V3/V2 proposals and original214-handler inventory; no generic SQL proxy. Remaining frontend engines/actions must be completed before calling their absence an integration blocker. Explicit owner approval is mandatory before production replacement.
